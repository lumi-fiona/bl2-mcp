# Feature backlog (agent claims, mechanisms UNVERIFIED)

## Shoot a chest to open it

Any lootable container pops open when you damage it, so you never walk up and press E on a crate again. Locked and paid containers (Golden Chest, slot machines) still need the normal use.

- why this user: It is the same taste as their auto-collect list: remove the pickup chore, do not hand out gear. It also survives co-op untouched, because it is the game's own UseObject call and the host arbitrates as usual. And it is the laziest possible feature - three hooks, no new state, no save data.
- mechanism (UNVERIFIED): Copy the shape of Zazk0u's open_sesame, which is already modern-SDK code in exactly their idiom. On `WillowGame.WillowInteractiveObject:InitializeFromDefinition` (Type.POST) set `this.bCanBeDamaged = True` and `this.bTakeDamageCausedByRadiusDamage = True` for any object where `wio.Loot and len(wio.Loot) > 0 and wio.Class is find_class("WillowInteractiveObject")`. Then on `WillowGame.WillowInteractiveObject:TakeDamage` and `:TakeRadiusDamage` (Type.PRE) call `this.UseObject(args.EventInstigator.Pawn, None, 0)` guarded by `wio.bCanBeUsed[0] == 1 and wio.bCostsToUse[0] == 0`. The bCostsToUse guard is the load-bearing one: it is what stops this becoming a free Golden Chest, which matters because their grinder lives on that chest.
- effort: under_an_hour | novelty: common_mod | testable alone: mostly
- precedent: Open Sesame by Zazk0u - https://bl-sdk.github.io/willow2-mod-db/mods/opensesame/ , source https://github.com/Zazk0u/new-bl-sdk-mods/tree/main/open_sesame
- risk: Setting bCanBeDamaged on every container lets damage-driven skills proc off crates - the mod's own comment names Anarchy specifically, so Gaige gains stacks from shooting boxes. In co-op the client's TakeDamage hook may fire on a replicated proxy and call UseObject with a Pawn the server rejects; blank prompt, no desync, but worth watching. No save-format contact at all, so no corruption path.

## Loot stops flying into the void

Dropped items stop bouncing off corpses and off each other, which is why loot ends up in geometry or in orbit. A key also gathers everything on the ground in front of you if something already escaped.

- why this user: They have Item Lights installed and built an extra co-op loot roll, so more loot hits the floor per kill than vanilla - which is exactly when the collision bug bites. The preventative half is four lines. This rescues gear rather than granting it, so it stays on the right side of their 'deliberately not gear' line.
- mechanism (UNVERIFIED): Prevention: hook `WillowGame.WillowPickup:EnableRagdollCollision` and, if `obj.CollisionComponent` exists, call `obj.CollisionComponent.SetRBCollidesWithChannel(16, False)` (dead pawns) and `SetRBCollidesWithChannel(24, False)` (willow pickups), then return Block. That is RedxYeti's whole mod. Rescue: a keybind that walks `get_pc().GetWillowGlobals().PickupList`, filters out `pickup.bIsMissionItem` and `pickup.bPickupable == False`, writes `pickup.Location = (x, y, z)` and calls `pickup.AdjustPickupPhysicsAndCollisionForBeingDropped()` (juso adds `InitializePickupForRBPhysics()` too). Lengyu's version has the co-op answer already: the client cannot move server-owned pickups, so it sends its PlayerID to a `@ServerMethod` which finds the matching `PRIArray` entry and does the move host-side.
- effort: a_few_hours | novelty: common_mod | testable alone: mostly
- precedent: Loot Collision by RedxYeti https://github.com/RedxYeti/Yeti-BL2-SDK-Mods/tree/main/LootCollision ; Be Gone Out Of Bounds Loot by juso https://github.com/juso40/bl2sdk_Mods/tree/master/BeGoneOutOfBoundsLoot ; Loot Collector by Lengyu https://github.com/aa3615058/Lengyu-BL2-sdk-Mods/tree/main/LootCollector
- risk: Blocking EnableRagdollCollision entirely also skips whatever else that native function does - the mod returns False rather than letting it run, so test that loot still settles on the floor instead of falling through it. The rescue key run from a client without the ServerMethod detour silently does nothing (Lengyu's code proves the author hit this). Teleporting a mission item is the one thing that could soft-lock a quest, hence the bIsMissionItem filter - copy it, do not improve on it.

## Reroll a mission reward for eridium

At the mission turn-in screen, a second key rerolls the two offered reward items for a small eridium cost, as many times as you can pay. In co-op both players get their own screen and reroll their own items.

- why this user: This is the biggest genuinely-loved feature they do not have, and it is the same engineering they already solved in the grinder: roll a balance out of a pool, build an item at a level, hand it over. It is also a real eridium sink for two people who are past the point where eridium does anything.
- mechanism (UNVERIFIED): ZetaDaemon's Reward Reroller. Block the vanilla grant path - return False from `WillowGame.WillowPlayerController:ServerGrantMissionRewards` and `WillowGame.MissionTracker:CompleteMission` - then drive it yourself. Rewards come from `mission.Reward` / `mission.AlternativeReward`, `.RewardItems` plus `.RewardItemPools`, each pool walked with `choices(items, weights)` where the weight is `Engine.Default__AttributeInitializationDefinition.EvaluateInitializationData(item.Probability, pc)`, and pools validated against `MinGameStageRequirement.GetValue(mission)`. Build with `pc.Spawn(inventory_definition.InventoryClass)` then `item.InitializeInventory(balance, manufacturer, level, None)` - the manufacturer walks up `balance.BaseDefinition` until `.Manufacturers` is non-empty. Push it to the screen with `pc.GFxUIManager.GetPlayingMovie().DisplayRewardsPage((mission, weapon_rewards, item_rewards, alt))` where the reward lists are exactly two `WeaponDefinitionData` and two `ItemDefinitionData` structs, padded with empties. The reroll key itself is caught in `WillowGame.QuestAcceptGFxMovie:HandleRewardInputKey` and `WillowGame.LatentRewardGFxMovie:HandleRewardInputKey`, charged via `PlayerReplicationInfo.AddCurrencyOnHand(ECurrencyType.CURRENCY_Eridium, -cost)`, and the prompt line is rewritten by returning False from `WillowGame.MissionRewardGFxObject:SetTooltips`.
- effort: most_of_a_session | novelty: common_mod | testable alone: needs_eyes
- precedent: Reward Reroller by ZetaDaemon (GPL3), source https://github.com/ZetaDaemon/bl-sdk-mods/tree/main/RewardReroller - itself derived from Flare2V and alienoliver's work in BL2Fix
- risk: This is the one on the list that can actually eat a mission. It suppresses the game's own CompleteMission and re-implements XP (`pc.ExpEarn`), currency and the reward grant; a bug in the co-op branch (`ServerMethod` -> `client_grant_rewards` -> `grant_rewards`) means a mission turns in with no reward and no way to get it back, and that state is then saved. It is also GPL3, so the code cannot be copied into their pack without licence contamination - the mechanism above is the thing to reimplement, not the file. Test on a copied save, never on the live one.

## Straight into your character on launch

The game skips the press-start screen, the SHiFT connection wait and the ads, and optionally loads a named character immediately. Startup goes from about a minute of waiting to a few seconds.

- why this user: They already tried this - `cleanmenu` and `fastboot` are written, disabled, and the note in features/__init__.py says the menu became unusable because closing the advertisement movies broke on the way back from a submenu. These mods do it a different way and do not touch the menu's own movie list, which is the specific thing that broke. One detail matters more than the rest: their community patch runner executes `set Transient.GearboxAccountData_1 ...` style commands, and apple1417 documents that forcing offline mode means GearboxAccountData_1 is never created - his workaround is to `construct_object` a dummy one so text-mod execs stop erroring. That is a bug their pack would otherwise walk straight into.
- mechanism (UNVERIFIED): Three pieces, all modern SDK. (a) Skip to menu: hook `WillowGame.WillowGameViewportClient:Tick` as Type.POST_UNCONDITIONAL, iterate `find_all("WillowGame.WillowGFxMoviePressStart")`, skip any where `obj.ObjectFlags & (0x400 | 0x200)`, and call `obj.BeginStartupProcess()` (safe mode) or the raw sequence `DoDlcEnumeration / DownloadPatcherFiles / DoSparkAuthentication / DoStartupDeviceSelection / CreateSession / ContinueToMenu`; disable the hook after one pass. (b) Auto-load a character: on `WillowGame.WillowPlayerController:ConditionalLoadDefaultSaveGame` call `obj.SetProfileSettingInt(116, save_id)`, then on `WillowGame.FrontendGFxMovie:Start` (POST) call `obj.LaunchSaveGame(get_pc().GetCurrentPlaythrough())`. The save id comes from `GetWillowGlobals().GetWillowSaveGameManager().SaveDataLoadedFromList[].SaveGameFileId`. (c) No SHiFT: on `WillowGame.WillowGFxMoviePressStart:DoSparkAuthentication` set `obj.ShouldStartSparkInitialization = False`, then set `Transient.GearboxAccountData_0.Services = (Transient.SparkServiceConfiguration_0,)` and construct a dummy `GearboxAccountData_1` with flags 0x4000. Ads are two lines on their own: Block `WillowGame.FrontendGFxMovie:ShowMOTD` and `WillowGame.WillowPlayerController:CanAcessOakUpsell`.
- effort: a_few_hours | novelty: common_mod | testable alone: needs_eyes
- precedent: Quick Startup by juso and mopioid (MIT) https://github.com/juso40/bl2sdk-mods/tree/main/quick_startup ; Offline Helpers by apple1417 https://github.com/apple1417/willow2-sdk-mods/blob/master/offline_helpers/Readme.md ; No Ads by apple1417 https://github.com/apple1417/willow2-sdk-mods/blob/master/no_ads/Readme.md
- risk: Their own note is the warning: a screenshot showed a perfectly clean menu every time the menu was broken, so this can only be signed off by someone clicking through Options and back into Mods. Forcing offline mode means no SHiFT codes and no golden keys from SHiFT - and their grinder lives on the Golden Chest, so check whether keys still arrive. Auto-loading a character in co-op means the second player lands in a session that already started; make it default-off and per-machine, not a shared setting the handshake compares.

## Alt-use a fast travel station to go where you are going

Holding the alternate use key on a fast travel station sends you straight to your current mission objective, or back to the station you last travelled from, without opening the map at all.

- why this user: They already run apple1417's Alt Use Vendors, so the interaction vocabulary is established and this reads as the same idea applied to travel. It is also per-playthrough remembered state, which is exactly the save_options.HiddenSaveOption pattern their levelless.py already uses.
- mechanism (UNVERIFIED): Yeti's Alt Use Fast Travel. `construct_object` a copy of `GD_InteractionIcons.Default.Icon_DefaultUse` with `flags=ObjectFlags.KEEP_ALIVE`, set `icon.Action = "UseSecondary"`, `icon.Icon = 5` and a text like TRAVEL TO OBJECTIVE. Attach it in `WillowGame.WillowInteractiveObject:InitializeFromDefinition` (POST) when `obj.Class.Name == "FastTravelStation"` by writing `args.Definition.HUDIconDefSecondary = icon` and calling `obj.SetUsability(True, 1)`. Act on it in `WillowGame.WillowPlayerController:PerformedSecondaryUseAction` (POST) with `obj.ServerTeleportPlayerToStation(find_object("FastTravelStationDefinition", path))`. The objective variant instead opens the station and reads `obj.CurrentWaypointStationDef` off `WillowGame.FastTravelStationGFxMovie:SetCurrentWaypoint`, skipping it if `bSendOnly` or if it names the map you are already in. One hack is load-bearing and worth copying deliberately: `WillowGame.TravelStation:SetUsability` is overridden by rebinding `func.func = find_class("WillowInteractiveObject")._find("SetUsability")` and calling the parent implementation, because TravelStation's own override refuses to mark the station secondary-usable. Last-station memory is stored per playthrough in three separate HiddenSaveOptions keyed off `get_pc().GetCurrentPlaythrough()`.
- effort: a_few_hours | novelty: rare_mod | testable alone: needs_eyes
- precedent: Alt Use Fast Travel by Yeti (GPL3) - https://bl-sdk.github.io/willow2-mod-db/mods/altusefasttravel/ , sdkmod at https://github.com/RedxYeti/bl2-willow2-sdkmods/raw/refs/heads/main/AltUseFastTravel/AltUseFastTravel.sdkmod
- risk: The mod db lists it Host Only. `ServerTeleportPlayerToStation` from a client is an RPC the host may refuse, and a fast travel that half-fires in co-op can leave one player in a map the other is not loading - the classic way to end a session. The icon object is constructed with KEEP_ALIVE and mutated in place, so reloading the mod twice in one session risks two icons fighting over HUDIconDefSecondary. No save writes beyond the station path string, so nothing here can corrupt a character.

## Restock the vendor you just used

One key rerolls the stock of the last vending machine you opened, with no save-quit and no walking away. Useful for shopping for a specific gun and for spending money that has nothing left to buy.

- why this user: They asked for one-button ammo and health at vending machines and got it from Alt Use Vendors; this is the other half of the vendor experience. Co-op Save Quit already restocks vendors but costs a full map reload for both players - this costs a keypress and does not interrupt the girlfriend. It is also two hooks total.
- mechanism (UNVERIFIED): Lengyu's Shop Reseter, which is about fifteen real lines. Capture the machine on `WillowGame.VendingMachineExGFxMovie:extInitVendingMachine` by storing `caller.VM`. On the keybind, verify the stored object is still live (`self.Shop.ObjectFlags.A == 0x4100000` in the legacy SDK; in the new SDK check the object still resolves) and call `get_pc().ServerPlayerResetShop(self.Shop)`. That is a server RPC the game already exposes, which is why the author notes it works from a client in multiplayer.
- effort: under_an_hour | novelty: common_mod | testable alone: mostly
- precedent: Shop Reseter by Lengyu (MIT) - https://github.com/aa3615058/Lengyu-BL2-sdk-Mods/tree/main/ShopReseter
- risk: Holding a raw UObject pointer across a map change is a use-after-free waiting to happen - that is what the ObjectFlags check is defending against, so do not drop it. Rerolling a shop is server state, so in co-op the girlfriend's open vendor screen will change under her; gate it on the machine not currently being used. Nothing touches the save.

## Dials for going down and getting up

Set how long reviving a teammate takes, from instant to ten seconds. Optionally, friendly NPCs run over and revive you when you are in Fight For Your Life and nobody else can.

- why this user: They asked for cheaper dying and got the money half; this is the time half, and it is the co-op half. Their coopfixes.py already flips bResurrectAllPlayersWhenOneDies and bEnemiesForgetDownedPlayers, so the revive rules are already a page they own. The dial itself is literally one float, which fits the everything-configurable rule at almost no cost.
- mechanism (UNVERIFIED): The dial: `find_object("InjuredDefinition", "GD_PlayerShared.injured.PlayerInjuredDefinition").ReviveDuration`, vanilla 5.0, keep-alive it and write the float on option change. That is the whole of RedxYeti's Revive Time Modifier. The NPC half is juso's NPCRevives and is much bigger: on `WillowGame.WillowPlayerPawn:SetupPlayerInjuredState` collect `find_all("WillowMind")[1:]` filtered by `mind.MyWillowPawn.IsFriendly(caller)` and a blacklist of pet AIClasses (Deathtrap, Scorpio turret, Bloodwing), sort by distance, then each tick of `WillowGame.WillowPlayerPawn:injured.Tick` drive them with `mind.ScriptedStance = 2`, `mind.ScriptedFocusStyle = 1`, `mind.ForceMoveToActor(target)`. When one is within range, fire `target.Controller.ReviveTarget = target` and `target.SetBeingRevived(True, target)`. It also has to fight the AI scheduler: return False from `WillowGame.Action_GoToScriptedDestination:SetMoveNode` for those minds and kick `GearboxFramework.ActionSequence.Update` with InterruptLatentAction/StopSequence/Stop/Start to wake idlers, then restore each mind's saved ScriptedStance in `ClearPlayerInjuredState`.
- effort: a_few_hours | novelty: rare_mod | testable alone: mostly
- precedent: Revive Time Modifier by RedxYeti https://github.com/RedxYeti/Yeti-BL2-SDK-Mods/tree/main/ReviveTimeModifier ; NPCRevives by juso (MIT) https://github.com/juso40/bl2sdk_Mods/tree/master/NPCRevives
- risk: ReviveDuration is a shared game-data object, so in co-op only the host's value is likely to matter and the two players can disagree about how long a revive took - put it behind their existing handshake so both machines carry the same number. NPCRevives permanently rewrites AI state on live minds and restores it from a Python-side snapshot; if the player leaves FFYL by dying rather than being revived, or the map unloads mid-revive, those NPCs can be left sprinting at nothing forever. It also revives one player at a time by design, which in a two-player game means it can pick the wrong one.

## Skill build slots

Save your current skill tree under a name and switch back to it later from the respec screen, instead of clicking thirty skill points back in one at a time.

- why this user: They ship free respec already, which turns respeccing from an expense into a chore - and this removes the chore. Builds are stored per character as JSON, which matches how their levelless gear feature already remembers per-character state. It is also the kind of thing a two-player household uses constantly, because one of you is always experimenting.
- mechanism (UNVERIFIED): Yeti's Skill Tree Loadouts. Save: walk `pc.PlayerSkillTree.Branches`, and for each `Branch.Definition.Tiers[].Skills[]` read the grade with `PST.GetSkillState(skill, make_struct("SkillTreeSkillStateData"))[1].SkillGrade`, writing `{branch_name: {skill_name: grade}}` plus a TotalCost that starts at 1 for the action skill. Load: check affordability against `pawn.GetExpLevel() - 4` (BL2's skill-point offset; TPS uses 2), then either `pc.ServerPurchaseSkillTreeReset()` or, for the free path, `pc.PlayerReplicationInfo.GeneralSkillPoints += pc.ResetSkillTree(True)` followed by `find_class('WillowLeviathanService').ClassDefaultObject.RecordPointsResetEventForPlayer(pc, 0, points)` and `bForceNetUpdate = True`. Then `pc.ServerUpgradeSkill(PST.GetActionSkill())` and one `ServerUpgradeSkill` call per point per skill. The UI is hung off the New-U respec button using `pc.GFxUIManager.ShowDialog(True)` with AppendButton entries - the same dialog machinery their grinder already drives through ui_utils.OptionBox.
- effort: most_of_a_session | novelty: common_mod | testable alone: mostly
- precedent: Skill Tree Loadouts by Yeti (GPL3) - https://bl-sdk.github.io/willow2-mod-db/mods/skilltreeloadouts/ , sdkmod at https://github.com/RedxYeti/bl2-willow2-sdkmods/raw/refs/heads/main/SkillTreeLoadouts/SkillTreeLoadouts.sdkmod
- risk: ServerUpgradeSkill is an RPC fired in a loop; on a client with latency the points can land out of order or be dropped, leaving a half-applied build and skill points spent on nothing. The free-respec path calls RecordPointsResetEventForPlayer directly, which is a telemetry function - if its signature is wrong the call is silent and the skill points are simply gone. Skill state is saved into the character file on the next autosave, so a bad load is a real save-affecting bug: take a backup first, which they already have machinery for.

## Stop the game saving while I experiment

A toggle that blocks every autosave until you turn it back on, with an on-screen indicator so you cannot forget it is on. Anything you did since the toggle is discarded when you reload.

- why this user: They built save backup, a sanity-check saver and a grinder that creates and destroys items, and their own writeup admits an earlier build charged the player and ate nothing. This is the seatbelt for that whole class of work: turn it on, try something, reload if it was wrong. It is also the cheapest feature on this list to build.
- mechanism (UNVERIFIED): infernumx's AutoSave Blocker: hook `WillowGame.WillowPlayerController:CanSaveGame` and return `(Block, False)` while the flag is set, `(Block, True)` otherwise. The indicator is drawn in `WillowGame.WillowGameViewportClient:PostRender` using `args.Canvas`: set `canvas.Font = find_object("Font", "UI_Fonts.Font_Willowbody_18pt")`, `canvas.SetPos(canvas.SizeX * x/1000, canvas.SizeX * y/1000, 0)`, `canvas.SetDrawColorStruct(make_struct("Color", r=..., g=..., b=..., a=...))`, `canvas.DrawText(text, False, scale, scale)`. That Canvas recipe is reusable - it is the same one every HUD mod in the database uses.
- effort: under_an_hour | novelty: common_mod | testable alone: fully
- precedent: AutoSave Blocker by identity/infernumx (GPL3) - https://bl-sdk.github.io/willow2-mod-db/mods/autosaveblocker/ , sdkmod at https://github.com/infernumx/bl-sdk-mods/releases/download/auto-save-blocker/auto_save_blocker.sdkmod
- risk: The failure mode is forgetting it is on and losing an evening - which is why the on-screen indicator is not optional decoration, it is the feature. In co-op saving happens per player on their own machine (Co-op Save Quit's page says exactly this), so one player blocking saves while the other does not means the two characters drift apart in mission progress. Blocking CanSaveGame unconditionally also blocks the save on quit; decide deliberately whether the toggle should auto-clear on map change.

## A marker on the map when something good drops

Every legendary or better that hits the ground puts an icon on the compass and the map, optionally with a sound. It disappears when someone picks it up.

- why this user: Two people fighting the same mob means two people who did not see where the orange landed - and they added an extra co-op loot roll, so it happens more in their game than in anyone else's. It is also the natural partner to the Item Lights they already installed: lights work in the room, a marker works through a wall.
- mechanism (UNVERIFIED): juso's LootMarker. There is no API for adding a minimap icon, so it fakes one: `ConstructObject(Class="InteractiveObjectDefinition", Name=...)` with the `RadarIconType` field set (the enum runs 0..16; the author found only Shop=4, Health=5, CatchARide=7, TravelStation=14, CustomizationStation=15 and LevelTransition=16 actually render, and defaults to CustomizationStation), then spawns a dummy actor at the loot's position via `find_all("WillowPopulationMaster")[-1].SpawnPopulationControlledActor(io_def.InteractiveObjectClass, None, "", loc, (0,0,0))` followed by `SetGameStage(1)`, `SetExpLevel(1)`, `InitializeFromDefinition(io_def, False)`. Drops are caught on `Engine.WillowInventory:DropFrom` and `WillowGame.WillowPickup:EnableRagdollCollision`, position is chased on `WillowGame.WillowGameViewportClient:Tick` while the item is still moving, and the marker is destroyed from `WillowGame.WillowPickup:PickedUpBy` and on `WillowClientShowLoadingMovie`. The sound is `FindObject("AkEvent", "Ake_UI.UI_HUD.Ak_Play_UI_Alert_CoOp_Ding")`.
- effort: a_few_hours | novelty: rare_mod | testable alone: needs_eyes
- precedent: LootMarker by juso (MIT) - https://github.com/juso40/bl2sdk_Mods/tree/master/LootMarker
- risk: Spawning real population actors per drop is the risky part: SpawnPopulationControlledActor consumes population budget, and a leaked marker is a live actor that persists across the map. The PickedUpBy and loading-movie cleanups are the only things stopping that leak, so both must fire. In co-op the markers are spawned by whoever is running the mod and may replicate to the other player as ghost objects. It writes nothing to the save.

## A health bar for named enemies

Bosses and badass-named enemies get the game's own boss health bar at the top of the screen, not just the handful Gearbox chose to enable it for.

- why this user: Pure taste, near-zero cost, and it makes their difficulty rebalance legible - if enemies are tougher now, a bar is how you feel that rather than guess it. The widget already exists in the game; nothing is being drawn from scratch.
- mechanism (UNVERIFIED): juso's Bossbar, which is about twenty real lines. On `WillowGame.WillowPawn:TakeDamage`, if no boss is currently tracked and `caller.IsChampion() or caller.IsBoss()`, store the pawn and call `get_engine().GetCurrentWorldInfo().GRI.InitBossBar(True, pawn)`. On `WillowGame.WillowPawn:Died`, if the dying pawn is the tracked one, call `GRI.UpdateBossBarInfo()` then `GRI.InitBossBar(False, None)` and clear it. IsChampion is the badass check, IsBoss the named-boss check, so both are the game's own classification rather than a hardcoded list.
- effort: under_an_hour | novelty: common_mod | testable alone: needs_eyes
- precedent: Bossbar by juso (MIT) - https://github.com/juso40/bl2sdk_Mods/tree/master/bossbar
- risk: It tracks exactly one pawn, so in a two-player fight with two badasses the bar shows whichever was hit first and ignores the other; and if the tracked pawn despawns without calling Died the bar sticks on screen at whatever value it last had. GRI is replicated state, so calling InitBossBar from a client may either do nothing or fight the host's own boss bar - test on both machines before shipping it on. Nothing near the save.

## Print the real damage number

Damage numbers on screen stop being useful above about six digits because the game truncates them. This logs the true figure, plus the target's name and level, to the console.

- why this user: They built enemy level scaling, a difficulty rebalance and gear that levels with you, and have an MCP bridge for reading the game from outside. This is the measuring instrument for all three - the difference between 'the rebalance feels harder' and a number. It is about thirty lines and they can pipe it straight into game_log.
- mechanism (UNVERIFIED): apple1417's True Damage Logger, already modern SDK. Hook `WillowGame.WillowDamageTypeDefinition:DisplayRecentDamageForPlayer`, bail unless `args.PC is get_pc()`, then read `args.DamageEventData.TotalDamageForDamageType` and skip anything below a configurable digit threshold. Name the target from `damage_event_data.DamagedActor.AIClass.DefaultDisplayName`, refined by walking `actor.BalanceDefinitionState.BalanceDefinition.PlayThroughs` for the entry matching `get_pc().GetCurrentPlaythrough() + 1` and taking its DisplayName. Level from `actor.GetExpLevel()`. Log with `unrealsdk.logging.info`.
- effort: under_an_hour | novelty: common_mod | testable alone: mostly
- precedent: True Damage Logger by apple1417 (GPL3) - https://bl-sdk.github.io/willow2-mod-db/mods/true-damage-logger/ , source in https://github.com/apple1417/willow2-sdk-mods
- risk: Almost none - it is read-only, client-side, touches no game state and no save. The only real cost is log volume: this fires on every damage event, so a low digit threshold in a Bee-and-conference-call build will flood the console and their game_log tool with it. Default the threshold high and make it a slider.

## Patch proof-read — check that all 4,500 patch lines actually landed

After the pack applies the Community Patch, it reads every changed value back out of the game and reports which lines really took effect and which quietly did nothing. You get a number you can trust instead of "4072 commands run".

- why this user: They already lost 479 map-specific commands to a silent failure (core.py:401-408, BL2-WAKE-UP.md:113) and the ~370 map fixes are their top-priority item. core.py:238-241 says outright that a patch that fails looks exactly like a patch that had nothing to do — this is the missing check for the single largest feature in the pack.
- mechanism (UNVERIFIED): patchfile.commands_from() already yields each line as `set <ObjectPath> <Property> <Value>` (patchfile.py:150, ALLOWED=("set","set_cmp") at :35). Apply via core._run's pc.ConsoleCommand (core.py:303-317), then read back with unrealsdk.find_object(<class>, <ObjectPath>) + getattr(obj, prop) — the exact call form grinder.py:863 uses live. The class name for each path comes from the OpenBLCMM SQLite index already on disk (BL2-LEVERS.md:521, C:\Users\Lumi\AppData\Local\Temp\bl2data\data\BL2\data.db); probe first whether find_object("Object", path) matches by IsA, which would remove the DB dependency entirely. Ship it as a bridge script first, then a mod option that writes data/patch-verify.txt.
- effort: most_of_a_session | novelty: nobody_has_done_this | testable alone: fully

## Level-less gear stops working the moment you equip it

Only guns sitting in your backpack get brought up to your level. The gun in your hands — the whole reason to mark it — is skipped every time.

- why this user: Gap, and probably the largest one in the pack. Their words were 'i always wanted to make weapon level-less like the grenade but nobody has done it yet'. A grenade mod is always equipped; a weapon that only levels while stowed inverts the thing they asked for. BL2-WAKE-UP.md line 102 reports the proof case as 'a level 43 shotgun doing 416 damage became level 51 doing 770' — that test ran on a backpack gun.
- mechanism (UNVERIFIED): features/levelless.py:179 `relevel_all` does `items = list(pc.GetPawnInventoryManager().Backpack)` and nothing else. Equipped gear lives on two linked lists on the same manager: InventoryChain (equipped weapons) and ItemChain (shield, grenade mod, class mod, relic), each walked by following item.Inventory until None. Rebuilding an equipped weapon is not the same operation as rebuilding a backpack one — ClientAddWeaponToBackpack (line 145) puts the replacement in the backpack, so the flow has to be: build the replacement, confirm it exists, remove the original, then re-equip via the inventory manager rather than leaving the player holding nothing.
- effort: a_whole_project | novelty: nobody_has_done_this | testable alone: fully
- precedent: https://github.com/apple1417/willow2-sdk-mods/blob/master/SanitySaver/helpers.py — `get_all_items_and_weapons` at line 70 is the canonical walk: chain_starts from inv_manager.ItemChain and inv_manager.InventoryChain, `while item is not None: yield item; item = item.Inventory`, plus the Backpack pass and the two in-flight slots BackpackInventoryBeingEquipped / EquippedInventoryGoingToBackpack (lines 96-108) that a naive walk misses mid-swap. Sanity Saver is already installed here (PINNED-COMPONENTS.txt line 11), so this is a read of code already on disk.
- risk: The highest gear-loss risk of anything on this list. levelless.py:121-123 already records that AddBackpackWeaponFromDefinitionData 'accepted the data and added nothing', which deleted a gun during development; doing this to the weapon currently in the player's hands multiplies that. Also: this changes what is in the inventory chain, which is precisely what Sanity Saver serialises — get it wrong at save time and the item is gone from the save file, not just from the session. Ship it behind its own option, default off, until it has survived a save-quit-reload cycle.
